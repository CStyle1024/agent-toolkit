# Git Commit

根据用户指令和当前任务创建范围准确的本地提交，保留其他工作。范围明确且用户已要求提交时，直接执行，不重复询问确认；若用户只要提交信息，则仅生成信息。

## 工作流程

1. **读取规范与现场。** 确认仓库根目录、当前分支与 HEAD；读取适用的 `AGENTS.md`、`CLAUDE.md`、提交规范及模板（包括 `git config --get commit.template` 指向的文件），参考近期 `git log` 的实际格式。检查 `git status --short --branch`、暂存区、未暂存修改和未跟踪文件；分别阅读 `git diff --cached`、`git diff` 及拟纳入的未跟踪文件内容，不能只看文件名或统计。记录提交前已有的暂存内容和其他修改。
2. **确定范围。** 以用户明确指定范围和本次任务上下文为准，不把所有脏文件默认视为本次任务。仅在无法判断修改归属时询问。同一文件混有多项任务时按块或补丁分离；无法可靠分离时说明具体重叠并等待范围澄清，不整文件带入提交。不顺手修复或提交无关问题。
3. **执行必要检查。** 根据实际改动及仓库要求选择有针对性的测试、静态检查或构建，不默认执行大型项目全量构建。记录命令、结果，以及未执行检查的原因；检查失败时说明影响，不声称通过，不擅自扩大修复范围。确保检查针对拟提交内容；若只检查了含其他修改的工作区，明确此限制。
4. **精确准备提交。** 仅暂存本次任务的路径或改动块，不使用 `git add .`、`git add -A` 或 `git commit -a` 全量纳入修改。已有的无关暂存内容必须保持暂存且不得进入本次提交；必要时使用隔离的临时 index 构造提交，提交后保持真实 index 与新 HEAD 一致，同时保留原有无关暂存差异和工作区内容。不得简单提交整个现有 index，也不得盲目用旧 index 覆盖提交后状态。若不能可靠保护这些内容，说明阻碍后询问，不冒险操作。
5. **编写信息并复核。** 用户提供 Jira 问题链接或 case id 时，先执行下方“Jira / case 信息与改动匹配”规则。优先使用仓库规定的格式、语言和模板；无规范时采用 Conventional Commits，以中文描述实际改动和有证据支持的原因，例如 `fix(scope): 修复具体问题`，必要时在正文解释原因。不编造测试结果、问题编号或变更原因。确认项目使用 Gerrit 时，遵守其模板和 Change-Id 规则，保留合法的既有标识或通过项目规定的机制生成，不伪造。提交前阅读最终拟提交 diff，核对路径、改动块、提交信息及与预期范围的一致性；使用临时 index 时检查该 index 的 diff。
6. **提交并核实。** 无可提交改动时明确说明，不创建空提交。执行普通本地 `git commit`，正常运行 hooks；失败时记录原因、检查是否留下修改，不跳过 hooks、不盲目重试。只有明确原因且修复在授权范围内时才修复后重试。成功后用 `git log -1`、`git show` 和 `git status` 核实 hash、完整提交信息、实际提交内容及剩余状态，确认无关工作区修改和暂存差异仍被保留。hooks 若改变内容，也必须检查最终产物。

## Jira / case 信息与改动匹配

当用户提供 Jira 问题链接或可定位的 case id 时，在生成提交信息前：

1. 使用当前环境可用的 Jira 连接器或已授权 API，获取该问题的编号、标题（`summary`）和描述（`description`）；仅获取编写提交信息及核验改动对应关系所需的信息，不修改 Jira 问题。
2. 若链接指向的问题编号与用户提供的编号不一致，先向用户澄清并等待答复，再生成提交信息，不自行选择其一。
3. 若项目提交规范要求使用 Jira 原始标题，直接将获取到的 `summary` 用作变更摘要，不自行概括、翻译或添加“修复”等前缀；编号及其他字段按项目模板填写。
4. 获取失败、无可用连接器或已授权 API、或缺少访问权限时，请用户提供原始标题；编号尚未确认时也请用户补充或确认。在获得所需信息前，不推测内容或生成依赖这些信息的提交信息。

5. **核验 case 与改动的对应关系。** 能读取问题信息时，根据描述中的问题现象、触发条件、预期行为或需求，对照本次拟提交的实际 diff 及必要的相关代码，判断修改是否针对该 case。不能只凭编号、标题关键词或文件名认定匹配；也不能把工作区中不属于本次提交的修改作为匹配依据。
6. **不符时暂停提交。** 若描述与提交内容不符或发现具体矛盾，说明 case 编号、描述要点、实际改动及不符之处，明确提示可能提供了错误链接或 case id，请用户确认关联关系或提供正确 case；在得到答复前不执行 commit。此前笼统的“提交代码”授权不能代替这次确认。用户解释并确认关联关系后，记录说明并继续；若更换 case，则重新读取和核验。不擅自替换 case、改写原始标题或修改代码来迎合 case。描述缺失、不可访问或过于简略时，准确标记“未能核验”及原因，不虚报匹配或仅因此断言不符；需要澄清具体疑点时请用户补充描述。最终待提交内容或关联 case 改变时，重新核验。

## 授权边界

- 默认只做本地 commit；只有用户明确要求时才 push 或上传 Gerrit。授权本地提交不等于授权上传评审。
- 不自动 amend、`reset --hard`、丢弃修改或强制推送；不为提交成功而绕过 hooks。
- 不因参考历史格式而推断未经证实的问题编号、原因或 Gerrit 配置。

## 完成报告

输出 commit hash、完整提交信息、检查结果（通过／失败／未执行及原因），以及剩余未提交修改（区分已暂存、未暂存、未跟踪）。涉及 case 时，同时简述对应关系核验结果（匹配／不符／未能核验）、依据及用户对疑点的确认（如有）。未成功创建 commit 时，明确说明原因和当前状态。
