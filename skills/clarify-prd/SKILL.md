# PRD 需求澄清

将原始需求整理成一份有来源依据的**需求澄清记录**，与原文一起交给后续规格设计。目标是明确已写规则、暴露缺失决策，不承诺推导出“所有隐含需求”。

## 输入与输出

- 阅读用户指定的原文、修订记录、表格和可读取的图片附件。已有澄清记录时先读，保留稳定 ID 与确认历史。
- 记录材料的路径或 URL、版本、读取状态与权威性。仅在原文或用户明确指定时确定来源优先级；不要因内容较新、看起来详细或出现在图片中就自动覆盖其他来源。
- 关联材料在可用工具和授权范围内读取；读不到则注明“未读取/读取失败”及影响，继续处理独立内容。用户限制本地材料时遵从限制。
- 用 [assets/clarification-template.md](assets/clarification-template.md) 生成**单文档**。用户未指定位置时，沿用项目文档目录，否则写入 `docs/requirements/<主题>-clarification.md`。保留原始材料，不直接改写原 PRD。
- Android/车机场景另读 [references/android-checklist.md](references/android-checklist.md)；其他领域不用加载它。
- 需要参考部分答复合并、保留冲突历史的写法时，可查看 [references/clarify-prd-update/](references/clarify-prd-update/) 中的初始记录与更新记录样例。

## 分析与成文

1. **定范围**：区分背景愿景、功能清单、本期详细规则和已删除内容。范围不一致时并列记录并提问，不把背景自动变成本期可实施需求。修订已明示某项变化时保留这条证据，覆盖范围或生效条件不明只询问该部分，不退回“是否曾增加该能力”；这不赋予修订记录自动覆盖其他冲突材料的优先级。条件性范围外问题只在其纳入本期后展开。
2. **提取规则**：按可独立确认或改变的行为分配 `REQ-001` 等 ID。每项保留主体、触发、条件和可观察结果，以及数量、频率、作用域、例外和“等”等开放性措辞。来源用文件别名＋章节/表格条目，必要时加行号或原文短引；长表格不能只引一个包含全部内容的行号。
3. **控制粒度**：同一行为的权限/操作枚举放一项；条件与结果保持相邻。分支较多时用关联 REQ 的矩阵保存完整文案与行为，避免每个按钮、权限、句子单独编号，也不要把不同机制的结果合并。

   **按功能组织**：原文包含多个功能时，以原文功能名称分别设置需求小节，各自放置需求表及相关分支矩阵。总体范围、跨功能共性规则单列，不重复复制到各功能。待确认问题沿用相同功能分组，组内优先列阻塞问题；跨功能问题只登记一次并引用受影响需求。单一且简短的功能可用一张表。分类调整不重编号已有 REQ/Q，也不改变规则、证据或确认状态；功能分组用于阅读，不代表新增模块设计。
4. **分开证据与状态**：证据性质为原文明示、推断或建议；推断注明依据，建议不混入已写规则。状态说明该项已提取、部分待澄清、存在冲突或已有后续确认。原文明示不等于产品新增确认；仅某个边界未定时写出该部分，不把整条明确规则降为未知。
5. **登记问题**：为缺失、歧义、冲突、缺失依赖分配 `Q-001` 等 ID，关联受影响 REQ，说明会改变什么结果。冲突保留双方依据。能独立答复并改变不同规则的问题分别编号；同属“生命周期”不足以把去重、再次触发、行车转换打包为一个状态。既有复合问题拆分时保留父 ID 和稳定子 ID，分别追踪答复。优先处理范围、判定逻辑、权威依赖、行为与安全边界，再补其他问题；标明“阻塞哪些规则/非阻塞补充”，不把所有问题当成全局阻塞。
6. **确认与更新**：先产出可审阅记录。用户要求离线分析或批量问题时，不等待逐题答复；需要继续澄清时，优先问影响最大的相关问题。仅有真实答复时追加确认记录（问题、结论、确认人或来源、日期），并同步更新需求和问题状态。部分答复不关闭整个复合问题；新答复与旧结论冲突时保留历史并显式标为重开，不静默覆盖。

## 关键判断

| 情况 | 处理 |
| --- | --- |
| 原文明确要求，边界未写 | 保留明确要求，只询问缺口，不编造相反选项让用户重新决策 |
| AND/OR、时间关联、生命周期不明 | 保留原句，提出影响行为的具体问题，不自行选默认值 |
| 异常写 NA，或截图只有成功状态 | 记为材料未提供异常，不推定没有异常；只检查与当前行为有关的失败情景 |
| 删除线、草案和最终规则并存 | 标注历史/待确认状态，不复活删除项；优先级不明则提问 |
| 图片含时间、标注或示例值 | 不自动变成固定产品要求；与正文矛盾时保留差异 |

## 交付前核对

对照原文逐项复查有效规则、分支、枚举与例外；核对 REQ/Q 引用、未读依赖、真实确认记录和未决范围。删除重复与无影响的问题。不要用条目数、清晰度分数或“所有栏目填满”代替覆盖核对。

文档只回答“已写什么、还有什么未决”。不产出架构、接口、权限实现方案或任务拆分；原文已指定的技术约束照实保留。结束时说明产物位置、优先澄清的问题、交付限制，并区分**记录可用**与**相关需求已具备规格设计/实现条件**。不自动启动下游流程或提交代码。
